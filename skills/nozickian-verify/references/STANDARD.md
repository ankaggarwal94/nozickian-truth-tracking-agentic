# Proposed Nozickian verification standard

This skill uses Nozickian truth-tracking narrowly and method-relatively. For a factual claim, code behavior, manual step, tool-result assertion, or agentic output `p` produced by method `M`, verification requires evidence that the method would not assert or retain `p` in relevant nearby worlds where `p` is false, and would assert or retain `p` in relevant nearby worlds where `p` remains true.

## Required components

### 1. Claim-level decomposition

Every important factual artifact must be decomposed into atomic claims. A claim can be a sentence in prose, a code docstring, a stated API behavior, a manual step, a cited numerical/date claim, a tool-output statement, or an implied precondition.

Each claim record must include:

- `id`
- `claim`
- `importance`: critical, major, or minor
- `scope`
- `truth_status`
- `method`
- `evidence`
- `false_world_tests`
- `true_world_tests`
- `contradictions`
- `residual_risks`


### 1a. No automatic epistemic closure / downstream transmission

A `PASS` result for claim `p` does not automatically verify any entailed, summarized, downstream, deployment, safety, compliance, or action-authorizing claim `q`. Nozickian tracking is claim- and method-relative: a method may track `p` without tracking a later operational or deployment conclusion inferred from `p`.

Any such downstream `q` must be represented as its own claim or as an explicit `derived_or_downstream_claims` record with method `M`, evidence, false-world tests, true-world tests, contradiction review, and residual-risk assessment. Entailed but untested downstream claims are `UNVERIFIED` and must not inherit `PASS-TRACKED` or `PASS-SCOPED` from their source claims.

### 2. Real method M

`M` is the actual production and checking method, not a post hoc story. It should include prompt and system instructions, model, retrieval corpus, retriever settings, tools, tool versions, execution environment, traces, graders, human approvals, and release gate.

A method is incomplete if it omits the part that actually produced the output or omits the verifier/grader that accepted it. A citation checker is not the method if the output was generated by a separate model and retriever before the checker saw it.

### 3. Nearby false-world sensitivity

False-world tests must be relevant, nearby, and targeted to each claim. Examples:

- Stale source or wrong version.
- Corrupted or misleading retrieval.
- Citation that supports a sibling claim but not the asserted claim.
- Invalid tool output or missing tool execution.
- Dependency drift or environment mismatch.
- Contradiction injection.
- Negative-control task that should not trigger the claim.
- Mutation test that creates a nearby false implementation.
- Honeypot fixture with plausible but false details.

A false-world test passes only if the method rejects, revises, abstains, or flags the false claim. Merely observing a trace is not enough.

### 4. Nearby true-world adherence

True-world tests must show that the method preserves supported truths under benign variation. Examples:

- Paraphrased prompt with same factual target.
- Equivalent authoritative source substitution.
- Alternate valid tool sequence.
- Compatible version range.
- Different but correct code implementation.
- Reordered but equivalent documentation steps.

Adherence prevents brittle expected-path scoring from rejecting valid alternative methods. A verifier that catches falsehoods but rejects many nearby truths is not a complete truth-tracker.

### 5. Gate condition

A factual artifact is verified only when the method meets thresholds for both false-world rejection and true-world retention at the claim level and along the actual execution path. The certificate being judged may not lower the gate thresholds. Thresholds can be tightened by policy but cannot be relaxed by the artifact under review.

## Status labels

- `PASS-TRACKED`: all critical and major claims meet truth, method, sensitivity, adherence, evidence, and contradiction requirements, and there are no material method unknowns.
- `PASS-SCOPED`: all checked claims pass, but scope limitations or runtime unknowns remain and are explicitly recorded.
- `LIMITED`: no critical failures, but major/minor claims or important evidence requirements are missing.
- `FAIL`: at least one critical claim fails or the gate itself is bypassable.
- `UNVERIFIED`: artifact or method cannot be sufficiently identified.

## Anti-patterns

- Treating a citation as verification when the citation might be stale, irrelevant, or hallucinated.
- Treating groundedness to a retrieved context as truth when the context might be wrong.
- Treating a passing test suite as verification when nearby false implementations also pass.
- Treating LLM-as-judge output as verification without judge calibration and false/true-world probes.
- Treating traces as verification when they are merely observed rather than scored.
- Allowing a certificate to set its own passing thresholds below the package defaults.

## PASS-TRACKED upgrade audit

An upgrade from `PASS-SCOPED` to `PASS-TRACKED` is a separate verification claim. It must be represented by an upgrade audit bundle and must not be inferred from a package self-test, a human review, or a successful deterministic gate alone. The upgrade claim must state the method `M_upgrade`: the exact Claude Code version, plugin load path, model, effort level, command lines, evidence bundle path, live fixture run, formal artifact run, strict gate command, official validator outputs, and trace-authentication parser used.

A `PASS-TRACKED` upgrade requires all of the following:

- deterministic package validator, strict self-gate, regression evals, gate contracts, formal-runner contracts, and behavior manifest all pass;
- Claude Code live fixture evals execute through the loaded plugin rather than returning `UNVERIFIED_RUNTIME`;
- formal artifact verification executes with `--output-format stream-json`, `--include-hook-events`, `--plugin-dir`, `--require-claude`, and `--require-trace-auth`;
- the runtime transcript authenticates assistant-origin native `ntt-*` tool-use events and matching user-origin tool-result/completion events for every required verification lane;
- the generated formal certificate is rerun through `ntt_gate.py` in strict local evidence mode and returns `PASS-TRACKED`;
- official Claude Code validators pass, or else the result remains scoped and cannot certify full runtime compatibility;
- no downstream, deployment, safety, compliance, or action-authorizing conclusion inherits pass status from an upstream package or trace claim.

If any of those conditions is unavailable, missing, dry-run only, or scope-limited, the correct result is `PASS-SCOPED`, `LIMITED`, `FAIL`, or `UNVERIFIED_RUNTIME`, not `PASS-TRACKED`. The package file `references/PASS_TRACKED_UPGRADE_AUDIT.md` is the detailed operational checklist for this upgrade from PASS-SCOPED.
